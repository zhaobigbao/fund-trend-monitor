# 开发实践经验总结

本文档用于记录项目开发过程中实际遇到的问题、调试经验和好的实现方式。

后续每次开发功能模块时，如果遇到值得复用的实现方式、踩坑点或架构微调，应补充到本文档。

## 当前实践约定

- 开发功能前先阅读 `docs/ARCHITECTURE.md`。
- 架构相关变化写入 `docs/ARCHITECTURE.md`。
- 具体 coding 经验、调试问题、实现技巧写入本文档。
- 不把临时实现经验散落在对话或代码注释里，除非它能帮助理解当前代码。

## 已沉淀经验

### 1. 模拟数据也要按真实接口结构组织

即使第一阶段使用模拟数据，也应按照未来真实系统的资源结构组织，例如基金、走势、持仓、行业暴露、研报和 AI 结论分别暴露接口。

这样后续替换数据源时，可以优先改后台数据适配，不需要大面积重写前端页面。

### 2. 实时数据和季度持仓必须明确区分

基金走势可以分钟级刷新，但持仓数据通常来自季报，存在披露滞后。

开发展示逻辑时，不要暗示季度持仓等同于当前实时持仓。后续页面上也应该明确展示持仓季度、披露日期和数据来源。

### 3. AI 结论需要保留证据链

AI 趋势结论不能只是单独一句判断，应尽量包含：

- 输入数据范围
- 关键持仓或行业暴露
- 相关研报观点
- 置信度或不确定性说明
- 后续观察指标

这样用户更容易判断结论是否可信，后续也方便做审计和回溯。

### 4. 前端图表优先保持轻量

早期原型可以使用原生 Canvas 绘制趋势图，减少依赖和工程复杂度。

当后续需要更多交互能力，例如缩放、十字光标、指标叠加、同类基金对比时，再引入专业图表库会更合适。

### 5. 页面展示不承担复杂分析

前端负责展示和交互，复杂的指标计算、行业聚合、AI 结论生成应放到后台。

这可以避免同一套逻辑在多个页面重复实现，也方便后续增加定时任务和缓存。

### 6. 服务入口要保持薄

服务入口只负责启动服务和组合路由。模拟数据、分析计算、接口路由、静态文件服务应拆到独立模块里。

这样后续接入真实数据源、数据库或后台任务时，不需要在一个大文件里拆逻辑，维护成本更低。

### 7. 自选和预警先走 API

即使第一阶段使用内存状态，自选基金和预警也先通过 API 暴露。

这样前端交互方式会更接近正式系统，后续替换成用户账户、数据库持久化和规则引擎时改动更小。

### 8. 接口响应可以提前携带解释字段

预警响应除了标题和正文，还应返回触发条件。AI 结论除了摘要，还应返回数据范围和证据来源。

这些字段能帮助用户理解系统为什么得出结论，也方便后续做审计、回放和调试。

### 9. 本地服务默认监听本机地址

本地开发环境里，Node 服务监听默认地址可能触发权限限制。服务入口默认使用 `127.0.0.1`，需要调整时再通过 `HOST` 环境变量覆盖。

### 10. 路由处理函数要明确返回已处理状态

API 路由写入响应后，要返回明确的已处理状态。否则服务入口可能继续走静态资源处理，造成重复写响应头错误。

### 11. Git 初始化可能需要在本机终端执行

当前开发会话可能阻止创建 `.git` 目录。遇到这种情况时，可以先维护 `.gitignore`，再由用户在本机终端执行 `git init`、首次提交和远程推送。

### 12. 排名和调仓变化由服务层计算

同类基金排名、综合评分、季度持仓变化这类结果应在服务层生成，前端只负责展示。

这样后续替换为真实行情、季报解析和更复杂的评分模型时，不需要同步改多个页面。

### 13. 本地数据库文件不进 Git

SQLite 文件属于运行时数据，应放在 `data/` 下并通过 `.gitignore` 忽略。仓库只提交 schema、Provider、初始化脚本和种子数据。

这样既能让项目开箱可跑，又不会把本地状态、用户自选或未来真实数据提交到远程仓库。

### 14. 种子数据只负责初始化

`src/data/mockData.mjs` 现在是种子数据，不再是业务服务的直接数据源。服务层统一通过 Provider 读取数据。

这能让后续接真实数据源、数据库迁移、后台任务时少改业务逻辑。

### 15. 外部数据先同步入库，再由业务接口读取

真实基金数据接入时，不让前端直接请求第三方接口。先由 `src/dataSources/` 适配器拉取数据，再通过同步脚本写入 SQLite。

这样可以控制调用频率、保留数据快照，也能在第三方接口不可用时继续展示已有数据。

### 16. 真实数据和模拟回退要并存

历史净值同步成功后，趋势接口优先使用 `fund_nav_history`；没有同步数据时继续回退到模拟曲线。

这个回退机制能让开发环境开箱可跑，也避免外部接口异常直接打断页面。

### 17. 新导入基金要支持缺失数据空状态

从外部搜索导入的基金通常先只有基础信息和历史净值，季报持仓、行业标签、研报可能暂时缺失。

服务层和前端都要把这视为正常状态：持仓、持仓变化、行业暴露、研报和 AI 结论应返回可解释的空状态，而不是抛错。

### 18. 同步状态要可见

真实数据接入后，页面必须显示数据来源、记录数和最新净值日。用户需要能判断走势图是来自真实净值历史，还是因为未同步而使用模拟回退。

同步状态由服务层从 `fund_nav_history` 和 `sync_runs` 计算，前端只展示结果。

### 19. 手动同步也要走服务层

页面上的手动同步按钮只调用本项目 API。API 由服务层统一拉取外部数据、写入 SQLite、更新基金快照并记录 `sync_runs`。

这样后续替换数据源或加入队列任务时，前端不需要改动。

### 20. 批量同步先顺序执行

当前批量同步自选基金采用顺序执行，避免在原型阶段对外部数据源造成并发压力。

每只基金无论成功或失败都应写入 `sync_runs`，页面展示真实同步记录，而不是前端临时状态。

### 21. 用户管理信息与外部基础资料分离

基金分组、标签和备注属于用户本地管理信息，不应写进 `funds` 基础资料表。

外部资料同步会刷新基金名称、净值、更新日期等字段，但不应该覆盖用户自己维护的观察分组和备注。独立的 `fund_pool_profiles` 表更适合承接后续组合观察、任务调度和 AI 结论偏好。

### 22. 本地移除基金要走统一数据层

移除本地基金时，不让前端逐个调用自选、净值、持仓等删除接口。

数据层删除 `funds` 主记录后，由外键级联清理关联表；同步记录这类没有外键的运行日志，再由同一数据层函数按目标基金代码清理，避免出现页面看不到基金但任务记录仍混在当前基金池里的状态。

### 23. 手工补录也是标准化入口

本地持仓补录不能绕过服务层直接写数据库。前端只提交用户输入，服务层负责校验季度、披露日期、来源和前十大持仓，再由 Provider 原子替换当前季度持仓。

如果补录的是新季度，旧的当前持仓需要沉淀为上一季度快照，避免持仓变化面板只显示“暂无变化”或丢失可比较的历史状态。

### 24. 股票标签从持仓行中独立出来

持仓行里的行业和赛道是披露快照，适合保留原始输入，但不适合作为长期标签库。

股票基础信息和行业、赛道、概念标签应沉淀到 `stocks` 与 `stock_sector_tags`。分析服务展示持仓和行业暴露时优先读取股票标签库，这样用户修正一只股票标签后，相关基金的行业暴露、研报匹配和 AI 证据链能一起更新。

### 25. 研报匹配要保留命中原因

研报不应只按行业粗粒度返回。更好的顺序是先匹配持仓股票，再匹配赛道，最后匹配行业。

接口返回时要带 `matchLabel` 和 `matchWeight`，让页面能解释研报为什么出现，以及它和当前基金持仓的关联强度。这样后续 AI 结论引用研报时也能保留证据链。

### 26. AI 结论先结构化，再展示

AI 结论不要只返回几段自然语言，否则后续页面、移动端和报告导出都很难复用。

这次把 `/api/funds/:code/insight` 固定成 `trend`、`risks`、`evidence`、`watchpoints` 四类结构，同时保留旧的 `bullets`、`actions`、`evidence` 字符串数组做兼容。前端只负责按栏目渲染，真正的趋势、风险、证据和观察指标仍在分析服务层生成。

结论文案要避免确定性买卖语言，尽量用“观察、验证、跟踪”表达后续动作；数据缺失时也要返回完整结构，并把低置信度和证据不足说清楚。

### 27. 定时刷新失败要安静降级

页面存在定时刷新实时估值的逻辑。开发时经常会重启本地服务，如果这类刷新失败直接抛错，会让浏览器控制台被重复错误淹没，影响真正问题排查。

定时刷新这类非关键链路应在前端捕获异常，保留当前页面数据并记录低噪声提示；首屏加载、保存、同步等用户主动操作仍应显示明确失败状态。

### 28. 结论历史要做内容去重

AI 结论接口会被页面加载、刷新和切换基金频繁调用。如果每次调用都插入一条历史记录，用户看到的历史会被重复快照污染，后续复盘也不可信。

这次用结论核心内容生成签名：`headline`、`confidence`、`dataScope`、`sections`、`source` 完全一致时，不重复落库。生成时间不参与签名，因为它只表示接口调用时刻，不代表结论内容真的变化。

历史接口只读取 `ai_insights`，前端不在浏览器里拼“伪历史”。这能保证后续做周报、趋势复盘或审计时，数据来源一致。

### 29. 板块实时数据要能降级

板块实时雷达会访问外部行情源，稳定性比本地 SQLite 差。页面首屏不能因为板块源短暂不可用而整体加载失败。

实现上，`sector-radar` 接口在外部板块请求失败时返回空雷达和可读消息；只有用户主动执行“同步持仓/板块”时才把失败作为明确错误提示。这样既能接真实数据，也能保住主页面可用性。

### 30. 公开网页数据解析必须集中在 adapter

东方财富基金持仓页面返回的是 HTML 片段，概念板块接口返回的是字段名较短的 JSON。解析这类源数据时，字段映射、HTML 清理、股票标签推断都集中放在 `src/dataSources/eastmoneyFundSource.mjs` 和服务层，不散落到前端。

这样后续如果改成 AKShare、Tushare 或商业 SDK，只需要替换 adapter 和 source selection，不需要重写页面。

### 31. 基金详情页按信息密度组织布局

持仓明细、AI 结论、研报列表这类内容密度高、阅读路径长的模块，不适合和另一个长模块并排放置。并排会导致用户横向来回扫视，也容易出现一侧被另一侧撑高的大块空白。

预警、行业暴露、板块实时雷达这类摘要型模块可以并列，但应固定同一行高度，超出内容在卡片内部滚动。这样页面扫描时先看主分析，再看摘要仪表盘，视觉秩序更稳定。

### 32. 同步任务入口集中到弹窗

数据源覆盖、净值同步、持仓/板块同步和同步记录都属于操作与状态管理。把这些内容放在主页面中间会打断用户查看走势、持仓和 AI 结论的路径。

更好的做法是在基金标题右侧保留一个“数据同步”入口，弹窗里集中展示同步动作和记录。这样主页面保持分析阅读优先，用户需要排查数据来源时也能快速进入同一个位置。

### 33. 候选数据源先入矩阵，不假装已接入

AKShare、Tushare、iFinD、Wind、Choice 这类数据源可以先进入能力矩阵和 UI 候选项，帮助用户理解后续扩展方向。

但在 adapter、token、SDK 或本地运行时没有完成前，前端选择项必须置灰，服务层也必须拒绝保存为当前来源。这样既能展示产品架构，又不会让页面给出“已经切换成功但实际仍用旧源”的误导。

### 34. 板块雷达用持仓权重打分，不用单一关键词

主动基金的持仓通常横跨多个赛道。像 000979 这类组合，CPO/光模块、AI服务器、AI PCB、铜金属和 AI 应用都可能同时影响净值。

板块实时雷达不能只用第一个匹配词找一个板块。更稳的做法是把持仓行业、赛道和别名词统一展开，并按持仓权重给候选概念/行业板块打分，再展示命中词和持仓交集权重。这样用户能看懂“这个板块为什么被选中”。

### 35. 实时源失败时先读缓存

板块实时接口依赖外部公开行情源，开发和真实使用时都可能遇到短暂 `fetch failed`。

如果之前已经成功同步过板块行情、成份股和分钟走势，服务层应该从本地缓存表重建雷达，并在消息里说明当前是缓存视图。这样页面不会因为外部源波动而直接空白，用户也能判断数据的新鲜度和可信度。

### 36. 重仓股贡献是近似归因

重仓股实时贡献用的是季报披露权重乘以个股当日涨跌，只能解释“如果持仓没有明显变化，哪些股票大概贡献了净值波动”。

实现上优先拉取个股实时行情，失败时可用板块成份股缓存里的个股涨跌回退。页面必须展示行情来源和匹配数量，文案用“估算、近似、贡献约”，不要把它写成基金最终净值或实时仓位。
