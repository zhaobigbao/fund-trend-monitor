# 整体架构设计规范

本文档统一维护基金检测网站的架构设计、模块边界、数据流和后续演进原则。

后续每次开发功能模块前，必须先阅读本文档，并确认新增功能是否符合当前架构边界。若实现过程中产生新的架构决策，需要同步更新本文档。

## 产品定位

本项目是一个基金研究与监测网站，目标是把基金实时走势、季度持仓、持仓股票所属板块/赛道、研报信息和 AI 趋势结论串成一套可持续扩展的研究工作台。

系统输出的是研究辅助结论，不应包装为确定性投资建议。

## 总体分层

系统按 6 层组织：

1. 数据接入层
   接入基金净值、实时估值、历史走势、季度持仓、股票行情、行业板块、概念赛道和研报数据。

2. 数据标准化层
   将不同来源的数据清洗成统一结构，例如基金、持仓、股票、行业、赛道、研报、AI 结论。

3. 分析服务层
   负责组合指标、行业暴露、持仓集中度、持仓变化、研报聚合、趋势判断等分析逻辑。

4. AI 结论层
   基于结构化数据和研报摘要生成趋势判断、风险提示、观察点和证据摘要。

5. API 层
   为前端提供稳定接口，屏蔽底层数据源差异。接口应该围绕业务资源设计，而不是围绕页面临时拼装。

6. 前端展示层
   提供基金监控、走势分析、持仓分析、研报情报、AI 结论等页面和交互。

## 核心业务模块

### 基金监测模块

职责：

- 基金搜索
- 本地基金池导入、分组、标签、备注和移除
- 自选基金列表
- 实时估值和涨跌
- 历史净值走势
- 阶段收益、回撤、波动等指标
- 同类基金对比

边界：

- 不直接处理研报内容。
- 不直接生成 AI 结论。
- 只消费标准化后的基金行情和净值数据。

### 持仓分析模块

职责：

- 展示季度持仓
- 本地补录基金季度持仓和披露信息
- 识别前十大重仓股
- 计算持仓集中度
- 展示新进、增持、减持、退出
- 聚合行业和赛道暴露

边界：

- 持仓数据以基金季报披露为准，存在天然滞后。
- 不把季度持仓等同于当前实时持仓。
- 本地补录是临时数据入口，应标记来源，后续可被真实季报解析结果替换或校验。

### 股票标签模块

职责：

- 维护股票基础信息
- 维护股票所属行业、板块、概念、赛道
- 为持仓分析和研报聚合提供标签能力

边界：

- 标签变化需要保留更新时间和来源。
- 同一股票可以属于多个赛道，但应有主行业。

### 研报情报模块

职责：

- 按股票、行业、赛道聚合研报
- 提取研报摘要、来源、发布时间、观点倾向
- 为 AI 结论提供证据材料

边界：

- 正式产品中必须确认研报数据授权和使用合规性。
- 不在前端直接暴露未经处理的大段研报原文。

### AI 趋势分析模块

职责：

- 生成基金趋势判断
- 识别持仓结构风险
- 总结行业/赛道研报观点变化
- 给出观察点和验证指标
- 生成周报、月报或事件触发分析

边界：

- AI 结论必须基于可追溯的数据输入。
- 结论应包含时间、数据范围和不确定性提示。
- 不输出确定性买卖指令。

### 预警模块

职责：

- 净值或估值异常波动预警
- 回撤预警
- 行业集中度预警
- 重仓股重大事件预警
- 研报观点显著变化预警

边界：

- 预警应是规则或模型判断结果，不代替用户决策。
- 每条预警需要能说明触发条件。

## 推荐页面结构

第一阶段建议页面：

- 基金监控首页
- 基金详情页
- 持仓分析页
- 研报情报页
- AI 分析报告页

页面只负责展示和交互，不承载核心业务计算。复杂计算应放在分析服务层或后台任务中。

## API 设计原则

API 应围绕业务资源拆分：

- `/api/fund-search?q=关键词`
- `/api/funds`
- `/api/funds?q=关键词`
- `/api/funds/import`
- `/api/funds/:code`
- `/api/funds/:code/profile`
- `/api/funds/:code/trend`
- `/api/funds/:code/holdings`
- `/api/funds/:code/holding-changes`
- `/api/funds/:code/sectors`
- `/api/funds/:code/peers`
- `/api/funds/:code/sync-status`
- `/api/funds/:code/sync-nav`
- `/api/funds/:code/reports`
- `/api/funds/:code/insight`
- `/api/funds/:code/alerts`
- `/api/watchlists`
- `/api/watchlists/sync-nav`
- `/api/sync-runs`
- `/api/alerts`

原则：

- 前端不直接拼接复杂业务逻辑。
- API 输出尽量稳定，方便后续替换真实数据源。
- 实时数据、季度数据、AI 结论需要带更新时间。
- 涉及基金持仓时，需要明确数据所属季度。

## 当前代码组织

当前第一阶段采用轻量 Node.js 服务、Node 内置 SQLite 和原生前端，不引入前端框架。

- `server.mjs`：服务入口，只负责组合 API 路由和静态资源服务。
- `src/data/mockData.mjs`：种子数据，用于初始化本地 SQLite，后续真实数据源接入后应逐步减少这里的业务数据。
- `src/data/sqliteProvider.mjs`：SQLite 数据 Provider，负责向服务层提供基金、持仓、研报、自选和预警规则数据。
- `src/dataSources/eastmoneyFundSource.mjs`：外部基金数据源适配器，负责基金搜索和历史净值拉取。
- `src/services/fundAnalytics.mjs`：分析服务层，负责走势、持仓、持仓变化、同类基金对比、板块暴露、研报聚合、AI 结论和预警规则。
- `src/services/fundImportService.mjs`：基金导入服务，负责外部搜索结果入库和初始净值同步。
- `src/services/fundHoldingService.mjs`：持仓管理服务，负责本地季度持仓补录、校验和任务记录。
- `src/services/fundPoolService.mjs`：基金池管理服务，负责本地分组、标签、备注和基金移除。
- `src/storage/database.mjs`：本地数据库 schema、建表和种子导入。
- `src/http/apiRouter.mjs`：API 层，负责业务资源路由。
- `src/http/staticFiles.mjs`：静态资源服务。
- `scripts/init-db.mjs`：数据库初始化脚本。
- `scripts/sync-fund-data.mjs`：基金基础数据同步脚本，将外部历史净值写入 SQLite。
- `public/`：前端展示层。

后续如果引入数据库、任务队列或模型服务，应优先新增 provider/service，不要把实现塞回前端页面或入口文件。

## 数据底座

当前本地数据库文件为 `data/fund-radar.sqlite`，属于运行时数据，不提交到 Git。

数据库启动策略：

- 应用启动时自动建表。
- 如果数据库为空，会从 `src/data/mockData.mjs` 导入种子数据。
- 可以通过 `npm run init-db` 手动初始化或校验数据库 schema。

当前已落库：

- 基金基础信息
- 当前季度持仓
- 上一季度持仓
- 持仓披露信息
- 研报摘要
- 自选基金
- 预警规则
- 历史净值
- 基金池管理信息：分组、标签、备注

外部数据接入策略：

- 外部数据源必须通过 `src/dataSources/` 下的适配器接入。
- 同步脚本负责把外部数据写入 SQLite，前端和 API 不直接请求第三方接口。
- 从外部搜索导入基金时，只写入基础信息和历史净值；持仓、行业和研报数据允许暂时为空。
- 趋势接口优先使用 `fund_nav_history` 中的真实净值历史；没有同步数据时回退到模拟曲线。
- 同步状态接口读取 `fund_nav_history` 和 `sync_runs`，向页面提供来源、记录数、最新净值日和最近同步结果。
- 页面手动同步通过 API 触发服务层同步，服务层负责调用外部数据源、写入 SQLite 和记录同步结果。
- 批量同步自选基金通过服务层顺序执行，并把每只基金的结果写入 `sync_runs`。
- 基金池管理信息存放在 `fund_pool_profiles`，与 `funds` 基础资料分离，避免外部基金资料刷新时覆盖用户本地观察信息。
- 从本地基金池移除基金时，由数据层删除 `funds` 主记录，并依赖外键级联清理自选、净值、持仓、披露和基金池资料；无外键的同步记录由数据层同步清理。
- 本地补录持仓通过持仓管理服务写入 `holding_disclosures` 和 `fund_holdings`；如果录入新季度，旧的当前持仓会转入 `previous_fund_holdings` 作为调仓变化计算快照。
- 正式产品需要确认外部数据源授权、调用频率和展示合规性。

## 数据模型规划

核心实体：

- `funds`：基金基础信息
- `fund_pool_profiles`：基金池本地管理信息，包括分组、标签、备注
- `fund_nav_history`：基金净值历史
- `fund_realtime_quotes`：实时估值
- `fund_holdings`：基金季度持仓
- `stocks`：股票基础信息
- `stock_sector_tags`：股票行业和赛道标签
- `research_reports`：研报元数据和摘要
- `ai_insights`：AI 分析结论
- `watchlists`：用户自选基金
- `alerts`：预警规则和触发记录

## 后台任务规划

建议后台任务：

- 分钟级：刷新基金估值和核心行情
- 日级：同步基金净值、股票行情和研报摘要
- 季度级：解析基金季报持仓
- 周级：生成基金趋势分析和组合观察报告
- 事件触发：重大涨跌、重仓股新闻、研报观点变化

## 开发约定

- 新功能开发前必须先阅读本文档。
- 涉及架构边界、模块职责、接口结构、数据模型变化时，必须更新本文档。
- 实现中遇到的具体问题、调试经验、好用写法，维护到 `docs/DEV_PRACTICES.md`。
- 页面层不要直接承担可复用的业务分析逻辑。
- 模拟数据应集中在数据适配层，避免散落在 UI 组件里。
- 后续接入真实数据源时，应优先替换数据适配层，尽量不改前端展示结构。
- 自选、预警、AI 结论这类状态或结果应通过 API 获取，避免只保存在前端临时状态里。
- 持仓接口必须返回 `quarter`、`disclosureDate` 和 `source`，前端必须展示这些信息，避免误导用户把季报持仓当作实时持仓。
- 同类基金对比和持仓变化属于分析服务层能力，前端只展示 API 结果，不在页面中重新计算排名或调仓结论。
- 运行时数据必须通过 Provider 读取；前端和分析服务不得直接读取 SQLite 文件或种子数据。
- 外部数据源不得直接耦合到页面层；新增真实数据接入时应先写 data source adapter，再写同步脚本或后台任务。
- 对于外部导入但尚未同步季报持仓的基金，分析服务必须返回稳定空状态，不允许因缺少持仓数据导致接口失败。
- 数据同步状态必须通过 API 暴露给前端，避免用户无法判断当前走势图来自真实数据还是模拟回退。
- 页面可以触发手动同步，但只能调用本项目 API，不能直接访问第三方数据源。
- 最近同步记录来自 `sync_runs`，前端不得根据按钮点击自行伪造任务记录。
- 本地持仓补录必须进入服务层校验和标准化后再入库，前端不得直接构造数据库形态。
